# L4LStore

A full-stack e-commerce web application built with React and Node.js. This project demonstrates a product catalogue, user authentication, shopping-cart flow, and admin-only product management backed by MongoDB.

**Live storefront:** [Open L4LStore](https://l4-l-website.vercel.app/)  
**Backend health:** [API health check](https://l4l-website.onrender.com/api/health)  
**Products API:** [Browse product data](https://l4l-website.onrender.com/api/products)  
**Source code:** [ChrisVu16-git/L4L-Website](https://github.com/ChrisVu16-git/L4L-Website)

> **Status:** The frontend is deployed on Vercel and the backend is deployed on Render. Product images are stored in Cloudflare R2. The new sandbox payment and email-confirmation flows require backend configuration and deployment. They are not verified against a real VNPay sandbox or SMTP sender yet. Do not enter real payment details.

## Features

- Browse products, view product details, search, and filter the catalogue
- Register and sign in using JWT-based authentication
- Shopping-cart and checkout/order screens
- Protect authenticated-user and admin-only pages
- Admin-protected product create, read, update, and delete (CRUD) API operations
- Validate product fields and handle malformed product IDs and API errors
- Upload product images directly to Cloudflare R2 using short-lived presigned URLs
- Store each product's public image URL and R2 object key in MongoDB
- Replace product images and clean up managed R2 images when they are no longer referenced
- Backend API tests using Node.js's built-in test runner and Supertest

## Product image upload architecture

L4LStore uses Cloudflare R2 for product image storage. Images are uploaded directly from the browser to R2; the image binary does not pass through the Express backend.

1. An administrator selects an image in the React admin dashboard.
2. The frontend sends the image's MIME type to `POST /api/uploads/image/presign`. The request includes the admin's JWT.
3. The Express route checks authentication and admin authorization, validates the image type, generates a unique object key under `products/`, and returns a presigned R2 PUT URL.
4. The browser uploads the file directly to R2 using HTTP `PUT` and the matching `Content-Type` header.
5. The frontend places the returned public image URL and R2 object key into the product form. Saving the product persists these values in MongoDB.
6. When a product image is replaced or a product is deleted, the backend checks whether the old R2 object is still referenced by another product before deleting it.

The presigned URL is temporary (five minutes) and is generated by the backend. The R2 object key is used for managed-image cleanup; the public URL is used to display the image in the storefront.

### R2 configuration

Create an R2 bucket in Cloudflare and configure its public URL for image delivery. Add the following variables to `mern-shop/backend/.env`:

```env
R2_ACCOUNT_ID=your_cloudflare_account_id
R2_ACCESS_KEY_ID=your_r2_access_key_id
R2_SECRET_ACCESS_KEY=your_r2_secret_access_key
R2_BUCKET_NAME=your_r2_bucket_name
R2_PUBLIC_URL=https://your-public-r2-domain
```

Use R2 S3-compatible credentials with access to the intended bucket. Never commit real credentials, paste them into issues, or expose them in frontend environment variables. Configure the same variables in the backend hosting provider's environment settings.

For browser uploads, configure the bucket's R2 CORS policy to allow the frontend origins you actually use. The policy needs the `PUT` method and the `Content-Type` request header. For local development and the deployed storefront, the origins currently used by this project are:

- `http://localhost:5173`
- `https://l4-l-website.vercel.app`

R2 bucket CORS is separate from the Express API's CORS configuration. If the frontend can load products but image uploads fail in the browser, check the R2 bucket CORS policy as well as the API response.

## Run locally

### Prerequisites

- Node.js and npm
- MongoDB (MongoDB Atlas or a local MongoDB instance)
- A Cloudflare account with an R2 bucket and credentials for image uploads

### 1. Clone and install dependencies

From your terminal:

```bash
git clone https://github.com/ChrisVu16-git/L4L-Website.git
cd L4L-Website/mern-shop
npm install
npm run install:all
```

### 2. Configure the backend

Create `mern-shop/backend/.env` with your own values:

```env
PORT=5000
MONGODB_URI=mongodb://127.0.0.1:27017/mern-shop
JWT_SECRET=replace_with_a_long_random_secret
CLIENT_URL=http://localhost:5173

R2_ACCOUNT_ID=your_cloudflare_account_id
R2_ACCESS_KEY_ID=your_r2_access_key_id
R2_SECRET_ACCESS_KEY=your_r2_secret_access_key
R2_BUCKET_NAME=your_r2_bucket_name
R2_PUBLIC_URL=https://your-public-r2-domain
```

Replace the MongoDB and R2 placeholders with your own values. Use a strong, private `JWT_SECRET`. Never commit real credentials or `.env` files.

### 3. Configure the frontend

Create `mern-shop/frontend/.env`:

```env
VITE_API_URL=http://localhost:5000/api
```

Vite reads `VITE_*` variables at build time. Rebuild and redeploy the frontend after changing the deployed API URL.

### 4. Start the application

From `mern-shop/`:

```bash
npm run dev
```

Default local URLs:

- Frontend: http://localhost:5173
- Backend health: http://localhost:5000/api/health
- Products API: http://localhost:5000/api/products

The backend connects to MongoDB when it starts. If database-backed routes fail, check `MONGODB_URI` and the backend logs. A successful health response alone does not prove database connectivity.

## Backend tests

The backend tests use Node.js's built-in test runner and Supertest. Configure a separate test database in `mern-shop/backend/.env`:

```env
TEST_MONGO_URI=mongodb://127.0.0.1:27017/mern-shop-test
```

Ensure `MONGODB_URI`, `TEST_MONGO_URI`, `JWT_SECRET`, and the R2 environment variables are configured. Then run:

```bash
cd backend
npm test
```

Run tests only against a database intended for testing, not production data; tests may create and delete test records.

To build the frontend, run from `mern-shop/`:

```bash
npm run build
```

## Continuous integration

GitHub Actions runs two independent workflows on pushes to `l4lstore-deployment`,
on pull requests targeting that branch, and via `workflow_dispatch`:

| Check | Working directory | Commands |
|---|---|---|
| Backend Tests / test | `mern-shop/backend` | `npm ci`, `npm test` (`node --test`) |
| Frontend Build / build | `mern-shop/frontend` | `npm ci`, `npm run build` (`vite build`) |

Both use Node.js 22 and cache npm downloads using the corresponding committed
lockfile. Each has a ten-minute timeout, read-only repository permissions, and
cancels older runs for the same ref. No path filters are used, so both checks
also report on documentation-only pull requests.

**Required secrets: none for these checks.** Backend CI starts a disposable
MongoDB 7 single-node replica set in Docker, waits for a writable primary, and sets `TEST_MONGO_URI` to its
local test database. The suite creates and removes records. Never replace this
URI with a production database. `JWT_SECRET` and all five `R2_*` values in the
workflow are deliberately fake test values. Existing R2 cleanup tests stub the
S3 client's `send` method; CI does not verify real R2 uploads, bucket CORS, or
live image deletion. Do not add production R2 credentials to this workflow.

Frontend CI uses `VITE_API_URL=/api` solely to check compilation. Vite exposes
`VITE_*` values in browser code, so these must never contain secrets. The build
neither starts nor calls the deployed API and does not deploy to Vercel or Render.
Deployment credentials and environment configuration remain with those hosts.
Automated frontend/browser tests are still a separate next step. Manual workflow
launches may only appear in GitHub's UI after the workflow exists on the default
branch; push/PR triggers are aligned to `l4lstore-deployment`.

The initial CI/storefront commit passed both GitHub Actions workflows. The subsequent
email-confirmation and sandbox payment changes add regression tests, including signed
IPN replay and transaction checks. Inspect the Actions run for the latest PR
commit before claiming that these expanded checks pass.

## Accounts and email confirmation

Register at `/register` with your name, email and a password of at least eight
characters (maximum 72 UTF-8 bytes). The form suggests `@gmail.com` when you type
an address without a domain; other providers are accepted. Server validation checks
address syntax, not mailbox existence. Ownership is established only by following
the emailed confirmation link and pressing **Confirm email**. It expires after
30 minutes and can be used once. Only the SHA-256 token hash is stored in MongoDB;
raw tokens are never returned by the API. Registration does not sign users in.

Set the following **backend-only** environment values (see `backend/.env.example`):

| Variable | Purpose |
|---|---|
| `SMTP_HOST`, `SMTP_PORT` | Mail server and port, usually 587 (STARTTLS) or 465 (TLS) |
| `SMTP_USER`, `SMTP_PASS` | SMTP sender credentials; use a Gmail App Password when using Gmail SMTP |
| `MAIL_FROM` | Authorized sender address, e.g. `L4LStore <your-sender@gmail.com>` |
| `CLIENT_URL` | Trusted frontend origin used in email links and VNPay return URLs |
| `JWT_SECRET` | Private application signing secret |

These belong in Render environment settings, never frontend `VITE_*` values or GitHub
CI secrets. Gmail SMTP commonly uses `smtp.gmail.com`; enable two-step verification
and create an App Password for the sender. Never use your normal Gmail password.
No personal Gmail API or Google OAuth login is needed for this SMTP integration.
A transactional mail service is preferable as traffic grows. SMTP submission does
not guarantee inbox delivery; check spam and provider logs.

`POST /api/users/register` queues no background job: it sends the email during the
request. Missing SMTP configuration returns 503 before creating an account. A send
failure after account creation leaves the account unverified; use **Resend confirmation**.
`POST /api/users/resend-verification` rotates the token, at most once per minute
per account. `POST /api/users/verify-email` accepts `{ token }`. Authentication and
verification endpoints share a 20-request / 15-minute per-IP limiter. Its in-memory
store resets on restart and is not shared between multiple server instances.

Existing accounts are unverified by default and must request a confirmation before
signing in. Previously issued JWTs are not revoked by this migration, but order creation
and checkout independently require a verified database user. No admin is automatically
marked verified. Confirm the admin account before deploying this change broadly.

## VNPay sandbox payments

VNPay 2.1.0 replaces the previous payment integration. Register a sandbox merchant
at [VNPay developer registration](https://sandbox.vnpayment.vn/devreg/) to obtain
`vnp_TmnCode` and `vnp_HashSecret`. Configure **backend-only** environment values:

```env
VNPAY_TMN_CODE=your_sandbox_terminal_code
VNPAY_HASH_SECRET=your_sandbox_hash_secret
VNPAY_RETURN_URL=https://l4l-website.onrender.com/api/orders/vnpay/return
VNPAY_USD_TO_VND_RATE=your_chosen_sandbox_conversion_rate
CLIENT_URL=https://l4-l-website.vercel.app
TRUST_PROXY_HOPS=0
```

For local development use `http://localhost:5000/api/orders/vnpay/return`.
`TRUST_PROXY_HOPS` must match your verified reverse-proxy topology; set it to `1`
only when exactly one trusted proxy sits between customers and Express (check your
Render setup). The payment URL uses `req.ip`; arbitrary forwarded headers are not
trusted by default. Incorrect proxy configuration can pass the proxy's IP to VNPay
and can also affect authentication rate limiting.

The gateway URL is fixed in code to `https://sandbox.vnpayment.vn/paymentv2/vpcpay.html`.
There is no production gateway switch. Use only sandbox merchant credentials and
VNPay's current test bank/card details; real payments are outside this implementation.
Remove the old Stripe environment variables and disable its old webhook endpoint.
The Stripe SDK and active webhook route have been removed. Historical paid orders
and their stored provider/session data are retained; unpaid orders can start VNPay
checkout. Do not switch a real merchant with outstanding payments without reconciliation.

### USD catalogue and VND payment quotes

Catalogue and existing order prices remain USD. VNPay supports VND, so configure an
explicit positive `VNPAY_USD_TO_VND_RATE` for sandbox quoting. There is no default
exchange rate and no live FX lookup. For example **only in tests**, a rate of 25,000
makes a USD 37.50 total become VND 937,500. This is an illustrative fixture, not a
current exchange-rate claim. Whole-VND rounding is applied once; VNPay receives the
VND amount multiplied by 100. Amounts outside VNPay's 12-digit protocol limit fail.

From an unpaid order choose **Review VNPay payment**. The server saves a 15-minute
quote/transaction reference, using the order's full total (items, tax and shipping).
The customer sees the VND amount, conversion rate and expiry before choosing
**Continue to VNPay sandbox**. Concurrent checkout requests reuse one stored quote.
Changing the configured rate does not change an existing unexpired quote.
Older attempts are retained for delayed IPNs. Failed IPNs allow a fresh attempt.
There is no stock reservation while the customer is at the payment gateway.

### Return URL and IPN

Configure VNPay with this public HTTPS **IPN** URL (server-to-server notification):

```text
https://l4l-website.onrender.com/api/orders/vnpay/ipn
```

The browser **return URL** and IPN are separate GET endpoints. Local IPN testing needs
a public HTTPS tunnel forwarding to port 5000; localhost is not reachable by VNPay.
Register the matching IPN URL with your sandbox merchant using VNPay's configuration
process. The return URL verifies the signature and quote, then redirects to the
frontend order page; it never marks an order paid or changes stock.

Both callbacks verify the sorted/encoded HMAC-SHA512 signature and terminal code;
duplicate query parameters are rejected. IPN also matches the stored reference and
exact amount. Successful payment requires both `vnp_ResponseCode=00` and
`vnp_TransactionStatus=00`, plus a valid VNPay transaction number. The backend does
not accept a frontend success flag as payment proof.

IPN responds with VNPay's `RspCode`/`Message` JSON: `00` acknowledges processing,
`02` acknowledges an already-paid order, `01` means unknown order, `04` wrong amount,
`97` bad signature/merchant, and `99` processing failure. A signed unsuccessful
payment is acknowledged without marking the order paid. Duplicate successful IPNs
cannot decrement stock twice: stock changes and paid status commit together in a
MongoDB transaction. Use Atlas or a replica set, not standalone MongoDB, for payment
fulfillment. Stock shortages return `99`; reconcile/restock or refund manually and
request IPN replay. VNPay retries are limited; do not rely on indefinite retry.
If multiple attempts somehow succeed for one order, only the first fulfills it;
additional payments require manual provider reconciliation/refund.

Automated tests cover a fixed independently computed HMAC fixture, callback tampering,
amount and terminal mismatches, concurrent quote creation, return-without-fulfillment,
failed payments, concurrent IPNs, and duplicate notification handling. No real VNPay
sandbox transaction or external callback delivery has been verified without merchant
credentials and a reachable configured IPN endpoint.

Official protocol reference: [VNPay 2.1.0 payment integration](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html).

## API overview

All endpoints are mounted under `/api`.

| Method | Endpoint | Access | Purpose |
|---|---|---|---|
| GET | `/api/health` | Public | Check API health |
| POST | `/api/users/register` | Public | Register a user |
| POST | `/api/users/login` | Public | Sign in and receive an authentication token |
| GET | `/api/users/profile` | Authenticated | Retrieve the current user's profile |
| GET | `/api/products` | Public | List products |
| GET | `/api/products/categories` | Public | List product categories |
| GET | `/api/products/:id` | Public | Retrieve a product |
| POST | `/api/products/:id/reviews` | Authenticated | Submit a product review |
| POST | `/api/products` | Admin | Create a product |
| PUT | `/api/products/:id` | Admin | Update a product |
| DELETE | `/api/products/:id` | Admin | Delete a product |
| POST | `/api/uploads/image/presign` | Admin | Generate a short-lived R2 image upload URL |

Admin product and image-upload operations require a valid token and admin authorization. Check the route and middleware files for exact access rules, request bodies, and response formats.
