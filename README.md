# L4LStore

A full-stack e-commerce web application built with React and Node.js. This project demonstrates a product catalogue, user authentication, shopping-cart flow, and admin-only product management backed by MongoDB.

**Live storefront:** [Open L4LStore](https://l4-l-website.vercel.app/)  
**Backend health:** [API health check](https://l4l-website.onrender.com/api/health)  
**Products API:** [Browse product data](https://l4l-website.onrender.com/api/products)  
**Source code:** [ChrisVu16-git/L4L-Website](https://github.com/ChrisVu16-git/L4L-Website)

> **Status:** The frontend is deployed on Vercel and the backend is deployed on Render. Product images are stored in Cloudflare R2. VNPay sandbox is configured on Render (reported by the project owner). Email confirmation is temporarily disabled. The external VNPay flow has not been independently verified in this change. Do not enter real payment details.

## Features

- Browse products, view product details, search, and filter the catalogue
- Register and sign in using JWT-based authentication
- Shopping-cart and checkout/order screens
- Protect authenticated-user and admin-only pages
- Admin-protected product create, read, update, and delete (CRUD) API operations
- Validate product fields and handle malformed product IDs and API errors
- Upload product images directly to Cloudflare R2 using short-lived presigned URLs
- Store each product's public image URL and R2 object key in MongoDB
- Replace product images and clean up managed R2 images when they are no longer referenced
- Backend API tests using Node.js's built-in test runner and Supertest

## Product image upload architecture

L4LStore uses Cloudflare R2 for product image storage. Images are uploaded directly from the browser to R2; the image binary does not pass through the Express backend.

1. An administrator selects an image in the React admin dashboard.
2. The frontend sends the image's MIME type to `POST /api/uploads/image/presign`. The request includes the admin's JWT.
3. The Express route checks authentication and admin authorization, validates the image type, generates a unique object key under `products/`, and returns a presigned R2 PUT URL.
4. The browser uploads the file directly to R2 using HTTP `PUT` and the matching `Content-Type` header.
5. The frontend places the returned public image URL and R2 object key into the product form. Saving the product persists these values in MongoDB.
6. When a product image is replaced or a product is deleted, the backend checks whether the old R2 object is still referenced by another product before deleting it.

The presigned URL is temporary (five minutes) and is generated by the backend. The R2 object key is used for managed-image cleanup; the public URL is used to display the image in the storefront.

### R2 configuration

Create an R2 bucket in Cloudflare and configure its public URL for image delivery. Add the following variables to `mern-shop/backend/.env`:

```env
R2_ACCOUNT_ID=your_cloudflare_account_id
R2_ACCESS_KEY_ID=your_r2_access_key_id
R2_SECRET_ACCESS_KEY=your_r2_secret_access_key
R2_BUCKET_NAME=your_r2_bucket_name
R2_PUBLIC_URL=https://your-public-r2-domain
```

Use R2 S3-compatible credentials with access to the intended bucket. Never commit real credentials, paste them into issues, or expose them in frontend environment variables. Configure the same variables in the backend hosting provider's environment settings.

For browser uploads, configure the bucket's R2 CORS policy to allow the frontend origins you actually use. The policy needs the `PUT` method and the `Content-Type` request header. For local development and the deployed storefront, the origins currently used by this project are:

- `http://localhost:5173`
- `https://l4-l-website.vercel.app`

R2 bucket CORS is separate from the Express API's CORS configuration. If the frontend can load products but image uploads fail in the browser, check the R2 bucket CORS policy as well as the API response.

## Run locally

### Prerequisites

- Node.js 22 LTS and npm (the same Node major used by CI)
- Docker with Docker Compose v2, or your own MongoDB Atlas database
- R2 credentials only for image uploads; VNPay sandbox merchant credentials only
  for external payments. Neither is required to start the shop.

### 1. Clone the deployment branch and install

```bash
git clone --branch l4lstore-deployment --single-branch https://github.com/ChrisVu16-git/L4L-Website.git
cd L4L-Website/mern-shop
npm install
npm run install:all
```

Already cloned? Commit or stash local edits first, then run from the repository
root. Do not reset or discard your work to resolve a pull error:

```bash
git fetch origin
git switch l4lstore-deployment
git pull --ff-only origin l4lstore-deployment
cd mern-shop
npm install
npm run install:all
```

All remaining commands below run from `L4L-Website/mern-shop` unless stated
otherwise. There is no `package.json` at the repository root.

### 2. Start MongoDB

```bash
docker compose up -d --wait --wait-timeout 90
```

Compose starts MongoDB 7, initializes the single-node `rs0` replica set and waits
for a writable primary. Port 27017 is bound to localhost only. Payments and
integration tests use transactions, which require a replica set or Atlas.
If port 27017 is already occupied by another local MongoDB, stop that service or
use Atlas instead. Inspect failures with `docker compose logs mongodb`.

Alternatively, use your own Atlas connection strings with distinct development
and test database names. Configure the Atlas database user and network access
for your machine. Do not use the deployed shop's production database for tests
or seeding.

### 3. Create environment files

macOS/Linux/Git Bash:

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Windows PowerShell:

```powershell
Copy-Item backend/.env.example backend/.env
Copy-Item frontend/.env.example frontend/.env
```

Replace `JWT_SECRET` in `backend/.env` with a private random value. Generate one:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

The example uses these local database settings:

```env
MONGODB_URI=mongodb://127.0.0.1:27017/mern-shop?replicaSet=rs0&directConnection=true
TEST_MONGO_URI=mongodb://127.0.0.1:27017/mern-shop-test?replicaSet=rs0&directConnection=true
CLIENT_URL=http://localhost:5173
```

For Atlas, replace both database URIs with your own distinct development/test
names. R2 example values are placeholders: configure real values only when
using image uploads. Leave VNPay merchant values blank until configuring payment.
Email confirmation is disabled; SMTP and Resend are not required.

`frontend/.env` should contain:

```env
VITE_API_URL=http://localhost:5000/api
```

Vite reads environment values at startup/build time. Restart it after changes.
Never copy backend secrets into frontend variables or commit `.env` files.

### 4. Optionally seed sample data

```bash
npm run seed
```

**Seeding deletes users and products in the database selected by `MONGODB_URI`.**
Use an isolated local/development database; skip seeding to preserve existing data.
It creates local accounts `admin@mernshop.com` / `admin123` and
`demo@mernshop.com` / `demo123`. The sample catalogue contains legacy USD prices
that the API displays in VND. These demonstration accounts are for local use only.

### 5. Start both services

```bash
npm run dev
```

- Frontend: http://localhost:5173
- Backend health: http://localhost:5000/api/health
- Products API: http://localhost:5000/api/products

Health alone does not prove database connectivity: also load products. An empty
list is valid if seeding was skipped.

### 6. Run checks in another terminal (from `mern-shop`)

```bash
npm test --prefix backend
npm test --prefix frontend
npm run build
```

The backend npm test script loads `backend/.env` for every test process.
Use a separate disposable `TEST_MONGO_URI`: tests create/delete fixture records.
Tests use fake R2 values and VNPay fixtures, so real provider keys are unnecessary.

### Local VNPay testing

Set your own sandbox terminal and hash secret in `backend/.env`. Keep
`CLIENT_URL=http://localhost:5173` and use the local return URL
`http://localhost:5000/api/orders/vnpay/return`. External payment confirmation
also requires a public HTTPS tunnel to port 5000 and that tunnel's IPN URL
registered with VNPay; VNPay cannot call your machine's localhost.
See [VNPay sandbox setup](#vnpay-sandbox-payments). Browsing, login, order placement
and fixture-based payment tests do not require a merchant account.

## Continuous integration

GitHub Actions runs two independent workflows on pushes to `l4lstore-deployment`,
on pull requests targeting that branch, and via `workflow_dispatch`:

| Check | Working directory | Commands |
|---|---|---|
| Backend Tests / test | `mern-shop/backend` | `npm ci`, `npm test` (`node --test`) |
| Frontend Build / build | `mern-shop/frontend` | `npm ci`, `npm test` (Vitest), `npm run build` (`vite build`) |

Both use Node.js 22 and cache npm downloads using the corresponding committed
lockfile. Each has a ten-minute timeout, read-only repository permissions, and
cancels older runs for the same ref. No path filters are used, so both checks
also report on documentation-only pull requests.

**Required secrets: none for these checks.** Backend CI starts a disposable
MongoDB 7 single-node replica set in Docker, waits for a writable primary, and sets `TEST_MONGO_URI` to its
local test database. The suite creates and removes records. Never replace this
URI with a production database. `JWT_SECRET` and all five `R2_*` values in the
workflow are deliberately fake test values. Existing R2 cleanup tests stub the
S3 client's `send` method; CI does not verify real R2 uploads, bucket CORS, or
live image deletion. Do not add production R2 credentials to this workflow.

Frontend CI uses `VITE_API_URL=/api` solely to check compilation. Vite exposes
`VITE_*` values in browser code, so these must never contain secrets. The build
neither starts nor calls the deployed API and does not deploy to Vercel or Render.
Deployment credentials and environment configuration remain with those hosts.
Frontend signup/login component tests run in jsdom; real browser end-to-end tests remain a next step. Manual workflow
launches may only appear in GitHub's UI after the workflow exists on the default
branch; push/PR triggers are aligned to `l4lstore-deployment`.

The initial CI/storefront commit passed both GitHub Actions workflows. The subsequent
email-confirmation and sandbox payment changes add regression tests, including signed
IPN replay and transaction checks. Inspect the Actions run for the latest PR
commit before claiming that these expanded checks pass.

## Accounts (email confirmation temporarily disabled)

Registration validates email format and password strength, creates the account,
and signs the user in immediately. SMTP/Resend configuration is not required.
Existing accounts can sign in and check out even when `emailVerified` is false.
Password hashing, JWT authentication, admin authorization, and authentication
rate limits remain active. No user is marked email-verified without proof.

Signup/login have no confirmation or resend controls. Previously emailed
`/verify-email` links redirect to sign-in. The backend `/api/users/verify-email`
and `/api/users/resend-verification` endpoints return HTTP 410 while disabled;
no confirmation emails are sent and old tokens are not consumed.

The dormant email transport utilities and their tests remain for possible future
re-enablement. Before restoring confirmation, configure a sender on Render and
restore the coordinated registration/login/checkout checks and frontend flow.
The current version does not need `RESEND_API_KEY`, `MAIL_FROM` or SMTP credentials.

## Guest checkout and account phone numbers

Visitors can continue from the cart through shipping, order placement and VNPay
sandbox payment without logging in. Shipping still requires a valid recipient name,
phone and complete address. Guest checkout does not create an account or associate
an order with an existing account just because a phone number matches.

Each guest order receives a cryptographically random private access code once at
creation. Only its SHA-256 hash is stored in MongoDB. The browser retains the code
for that order and sends it via `X-Guest-Order-Token`, never the URL. The receipt
shows a backup code under **Lưu mã tra cứu đơn hàng**. Save both its URL and code;
on another device enter the code to reopen it. Without the code, a phone number
or order ID alone cannot reveal the address, payment status or checkout link.
Admins can manage guest orders normally. Guest orders are not included in an
account's order history and are not automatically claimed when someone registers.

Guest order creation/checkout is rate-limited. Invalid supplied bearer tokens are
rejected rather than silently treated as anonymous. Admin mutations and account
order lists still require authentication. VNPay's signed return/IPN and stock
transaction rules apply equally to guest orders. Existing email confirmation remains
disabled. Phone validation checks format only; SMS/OTP ownership verification is
not implemented.

New accounts require a Vietnamese mobile phone number. Common input forms such as
`0912345678`, `+84 912 345 678` and `0084912345678` normalize to the same number.
**Tài khoản** lets users update their name/phone; a phone already used by another
account is rejected. A partial unique MongoDB index enforces uniqueness even under
concurrent registrations/updates. Existing accounts without a phone remain usable
and can add one later; no shared placeholder phone is assigned. Shipping phone
numbers are order contacts and do not change or reserve account phone numbers.
The same guest can place multiple orders with the same delivery contact number.

The application waits for the user indexes before registration/profile phone writes.
If manually inserted legacy user phone values already conflict, resolve those values
before building the unique index; do not disable the index to bypass conflicts.

## VNPay sandbox payments

Use the sandbox-only test card supplied by the project owner, or the current
[official VNPay sandbox guide](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html).
Do not use real card details.

A signed VNPay cancellation (`vnp_ResponseCode=24`) returns to the first product
in the stored order; multi-product orders use that first product, with the catalog
as a fallback for an empty order. Other failures stay on the receipt so payment
can be retried. Cancelling payment does not cancel the order, change stock or mark
it paid. The browser return continues to validate merchant, signature and amount.
No additional Render secrets are needed for this redirect.

VNPay 2.1.0 replaces the previous payment integration. Register a sandbox merchant
at [VNPay developer registration](https://sandbox.vnpayment.vn/devreg/) to obtain
`vnp_TmnCode` and `vnp_HashSecret`. Configure **backend-only** environment values:

```env
VNPAY_TMN_CODE=your_sandbox_terminal_code
VNPAY_HASH_SECRET=your_sandbox_hash_secret
VNPAY_RETURN_URL=https://l4l-website.onrender.com/api/orders/vnpay/return
CLIENT_URL=https://l4-l-website.vercel.app
TRUST_PROXY_HOPS=0
```

For local development use `http://localhost:5000/api/orders/vnpay/return`.
`TRUST_PROXY_HOPS` must match your verified reverse-proxy topology; set it to `1`
only when exactly one trusted proxy sits between customers and Express (check your
Render setup). The payment URL uses `req.ip`; arbitrary forwarded headers are not
trusted by default. Incorrect proxy configuration can pass the proxy's IP to VNPay
and can also affect authentication rate limiting.

The gateway URL is fixed in code to `https://sandbox.vnpayment.vn/paymentv2/vpcpay.html`.
There is no production gateway switch. Use only sandbox merchant credentials and
VNPay's current test bank/card details; real payments are outside this implementation.
Remove the old Stripe environment variables and disable its old webhook endpoint.
The Stripe SDK and active webhook route have been removed. Historical paid orders
and their stored provider/session data are retained; unpaid orders can start VNPay
checkout. Do not switch a real merchant with outstanding payments without reconciliation.

### VND prices and legacy records

The application interface is Vietnamese and prices are displayed as whole Vietnamese
dong. New product prices and orders explicitly store `currency=VND`. Product create
and edit APIs accept whole-VND prices. Cart/order summaries and VNPay use those VND
amounts directly; no second USD conversion or live exchange-rate lookup occurs.
`VNPAY_USD_TO_VND_RATE` is no longer required.

Existing records without a currency (or marked USD) use the user-approved fixed
conversion **1 USD = 25,000 VND**. Product/order read responses convert these values
without rewriting historical database amounts. Editing a legacy product converts it
to VND once and retains its old price in `legacyPriceUsd`; editing an order's shipping
or status does not rewrite its historical prices. Existing browser carts are converted
once on load and stored with a VND currency marker. Do not manually relabel old USD
records as VND without converting their amounts. During rolling deployments, read
responses without a currency marker are normalized by the frontend. Commerce writes
wait for a backend health response advertising `X-L4L-Currency: VND`. Product price
writes must explicitly include `currency: VND` and `X-L4L-Client-Currency: VND`, so old USD forms cannot overwrite
new VND prices. This compatibility rule is not a
current market exchange rate.

Shipping and demo tax preserve the previous configuration after conversion: shipping
is 250,000 VND, waived for an items subtotal above 2,500,000 VND; estimated tax is 10%,
rounded to whole VND. These are application demo settings, not a statement of tax law.

VNPay receives VND multiplied by 100. Customers review the amount and 15-minute
expiry before leaving the order page. Concurrent requests reuse the saved quote.
Old attempts remain valid for signature/amount verification of delayed IPNs.

### Shipping validation and order management

New orders validate recipient name, phone, street address, ward, province/city and
country in both browser and API. Postal code is optional. Vietnamese phone numbers
are normalized, including `+84` input. Validation checks format/completeness; it does
not geocode an address or prove that a recipient can receive delivery there.

Admins can filter orders by status, edit recipient/contact/address before shipping,
add a tracking number and internal note, and progress orders through **Đã đặt hàng →
Đang xử lý → Đang giao hàng → Đã giao hàng**. Customers see the same status, timeline
and tracking number on their order screens. Internal notes are excluded from customer
responses. Paid state remains controlled by VNPay IPN, not the admin editor.

Admin updates require the current `version` and reject stale writes with 409. Shipping
requires a paid order and tracking number. Backward status transitions are rejected.
Unpaid placed/processing orders can be cancelled. Paid orders require manual refund
reconciliation and cannot be cancelled through this editor. Cancelled orders cannot
start checkout; a late successful IPN returns a reconciliation error rather than
silently fulfilling a cancelled order. Historical orders infer delivered/placed status
from their existing delivery flag until first updated. The legacy deliver endpoint
uses the same payment, transition and version checks.

### Return URL and IPN

Configure VNPay with this public HTTPS **IPN** URL (server-to-server notification):

```text
https://l4l-website.onrender.com/api/orders/vnpay/ipn
```

The browser **return URL** and IPN are separate GET endpoints. Local IPN testing needs
a public HTTPS tunnel forwarding to port 5000; localhost is not reachable by VNPay.
Register the matching IPN URL with your sandbox merchant using VNPay's configuration
process. The return URL verifies the signature and quote, then redirects to the
frontend order page; it never marks an order paid or changes stock.

Both callbacks verify the sorted/encoded HMAC-SHA512 signature and terminal code;
duplicate query parameters are rejected. IPN also matches the stored reference and
exact amount. Successful payment requires both `vnp_ResponseCode=00` and
`vnp_TransactionStatus=00`, plus a valid VNPay transaction number. The backend does
not accept a frontend success flag as payment proof.

IPN responds with VNPay's `RspCode`/`Message` JSON: `00` acknowledges processing,
`02` acknowledges an already-paid order, `01` means unknown order, `04` wrong amount,
`97` bad signature/merchant, and `99` processing failure. A signed unsuccessful
payment is acknowledged without marking the order paid. Duplicate successful IPNs
cannot decrement stock twice: stock changes and paid status commit together in a
MongoDB transaction. Use Atlas or a replica set, not standalone MongoDB, for payment
fulfillment. Stock shortages return `99`; reconcile/restock or refund manually and
request IPN replay. VNPay retries are limited; do not rely on indefinite retry.
If multiple attempts somehow succeed for one order, only the first fulfills it;
additional payments require manual provider reconciliation/refund.

Automated tests cover a fixed independently computed HMAC fixture, callback tampering,
amount and terminal mismatches, concurrent quote creation, return-without-fulfillment,
failed payments, concurrent IPNs, and duplicate notification handling. No real VNPay
sandbox transaction or external callback delivery has been verified without merchant
credentials and a reachable configured IPN endpoint.

Official protocol reference: [VNPay 2.1.0 payment integration](https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html).

## API overview

All endpoints are mounted under `/api`.

| Method | Endpoint | Access | Purpose |
|---|---|---|---|
| GET | `/api/health` | Public | Check API health |
| POST | `/api/users/register` | Public | Register a user |

| GET | `/api/products/categories` | Public | List product categories |

| PUT | `/api/products/:id` | Admin | Update a product |

Admin product and image-upload operations require a valid token and admin authorization. Check the route and middleware files for exact access rules, request bodies, and response formats.
